# Phase 5a — Offline-first mobile scope

> **Status:** scope doc (not building yet).
> **Branch:** `ofp-monorepo` (current default).
> **Author:** agent audit + user-confirmed picks.

## TL;DR

Build the mobile app from a 50-line stub into a "his basement has no signal" job-list. New pieces: `expo-sqlite` local mirror, durable outbox, `POST /api/sync` server endpoint, pre-signed MinIO upload via `expo-file-system`, `version` column + Postgres trigger for last-write-wins conflict detection, and a long-lived mobile JWT gated by `users.active`. Est. ~25–30 files, one additive migration.

## 3. Five design decisions (ratified)

### 3.1 ID strategy: **client-generated UUIDs**

Switch off `defaultRandom()`; mobile supplies `crypto.randomUUID()` on every insert. Eliminates localId ↔ serverId remapping entirely, and the server is happy to accept a UUID as-is.

- **Cost**: schema migration replaces the default with no default — every existing row is unaffected; new rows must supply. API contract gains an `id` field on POST bodies.
- **Why not remap**: temp-id remapping across `lineItems.jobId` is a class of bugs (offline create-job + offline create-lineitem referencing the temp jobId, then desync if remap fails). Client UUIDs sidestep it.

### 3.2 Versioning: **integer `version` column + Postgres trigger**

Add `version integer default 1 not null` to 4 tables. Create a `BEFORE UPDATE` trigger that auto-sets `NEW.version = OLD.version + 1`. Sync payload includes `version`; server compares to stored; mismatch → `409 Conflict` with canonical row.

- **Cheaper alternative** was `updated_at`, rejected because device clocks drift on the devices this feature targets (field techs with old Android phones, no NTP).
- **Server compares**, never the client. Client always sends what it knew; server is the authority.

### 3.3 Outbox durability: **local SQLite**

`outbox` table on the device. AppState transition `background → active` calls `drain()`. Backoff is `1s, 5s, 30s, 5m, 5m, …` *but* the trigger is state-change-based, not a JS timer. When the app is alive but no events fire (e.g. backgrounded by user mid-outbox), `BatteryState`/~`AppState.active` from `react-native` is what wakes it; we register a foreground handler, not a `setInterval`.

### 3.4 Photo upload: **`expo-file-system.uploadAsync` to MinIO pre-signed PUT**

Server never sees the bytes. Mobile does `FileSystem.uploadAsync(url, fileUri, {httpMethod: 'PUT', headers})`. 15-minute URL TTL. Multi-megabyte photos don't OOM the RN bridge because `uploadAsync` streams.

- **The trap**: `fetch(file)` in RN loads the entire body in memory → OOM on a 12 MB dispatch photo.
- **Backup path**: if presign fails (MinIO down), the local copy stays on disk and a "retry upload" badge shows up next to the queued photo.

### 3.5 JWT: **10-year mobile JWT, gated by `users.active`**

Issue via existing `POST /api/auth/login`. Single long-lived token in `expo-secure-store`. `users.active` is the off-switch (owner demotes tech → server returns 401 on next sync → mobile clears secure store → login screen). No refresh token dance.

- **Threat model**: a stolen phone = a stolen 10-year JWT. Mitigation is server-side `users.active = false`, which we already have.
- **Why not short-lived + refresh**: refresh-on-mid-sync is brittle; the simplest robust thing is non-expiring + cheap revocation.

## 4. Ponytail-marked ceilings

Three shortcuts the architecture intentionally takes. Each `# ponytail:` comment must be in the actual code, not just this doc.

### 4.1 Outbox durability

```ts
// ponytail: outbox lives in local SQLite only; no BullMQ redrive.
// Ceiling: app reinstall wipes the queue silently. Phone theft same.
// Upgrade: server-side `pending_ops` table mirrored from mobile
//          (mobile posts each enqueue to /api/sync earlier, not
//          just on drain; install/loss becomes recoverable).
```

### 4.2 Conflict resolution = LWW by `version`

```ts
// ponytail: last-write-wins; no field-level merge, no human review UI.
// Ceiling: dispatcher edits office-side invoice total while tech
//          marks the job complete offline; whichever syncs last
//          wins outright, the other edit is silently discarded.
// Upgrade: surface conflicts in a `conflicts` log table + web UI
//          "Conflict: tech set status=completed but office set
//          total=$420; resolve? [keep office] [keep tech] [merge]"
//          (mirrors WatermelonDB-style pull-subscription conflicts).
```

### 4.3 Pre-signed PUT (no server proxy)

```ts
// ponytail: pre-signed URL upload; server does not see photo bytes,
//          no virus-scan, no resize.
// Ceiling: compromised MinIO creds = untrusted content straight to
//          bucket; no width/height fixup on display; no metadata
//          extraction; no CBOR/thumbnail.
// Upgrade: server signs only after a HEAD probe of the file (size
//          + MIME sniff); a worker Lambda pulls new uploads through
//          a virus-scan + thumbnail pipeline; signed GET with role
//          check (currently the bucket URL is the GET too).
```

## 6. Open questions (resolved)

1. **Router vs single-file mobile.** **Pick: stay single-file, add `@react-navigation/native` `Stack.Navigator` inside `App.tsx`.** Five screens in MVP doesn't justify the expo-router plugin + its file-per-screen convention. Internal stack is the lazy senior shape; if we hit double-digit screens later, the migration to expo-router is mechanical (rename `Stack.Screen name="…" component={X}` → `app/(tabs)/x.tsx`).

2. **Conflict log retention.** **Pick: `90 days`, hard-purged by daily cron after that.** Techs need to see "what did I lose last week"; auditors don't want customer PII indefinitely. Lands as `apps/api/src/cron/purge-conflicts.ts` scheduled on the existing `BullMQ` (already wired in §1 of the doc), single-line `DELETE FROM conflicts WHERE created_at < NOW() - INTERVAL '90 days'`. The job itself is a 5-line file; nothing fancy.

3. **`version` and `updated_at` on the other tables.** **Pick: add to 7 — `jobs`, `line_items`, `invoices`, `appointments`, `customers`, `estimates`, `payments`. Skip 4 — `properties`, `recurring_jobs`, `reviews`, `activities`.** The 4 skipped are read-mostly or never-edited offline: `properties` updates happen on the office side; `recurring_jobs` is owner-managed; `reviews` are customer-submitted from a web page; `activities` is an append-only log. Spending the version+trigger overhead on those is YAGNI. Spec §2.2 grows from "4 tables" to "7 tables"; one extra column, one extra trigger per table.

4. **MinIO GET signing.** **Pick: server-side `/api/uploads/signGet` route, 1-hour pre-signed TTL, generated on demand; bucket stays private; no Redis cache in MVP.** A 1-hour TTL keeps the bucket private with bounded exposure; pre-signing-on-render is ~1 ms API CPU per photo load — not worth a cache layer. Worst alternative (server-proxying GET bytes) would defeat the §4.3 pre-signed PUT ponytail and re-introduce the OOM-and-network-bottleneck the PUT path is specifically avoiding.

## 7. Acceptance criteria

- A tech can mark a job `completed`, add 3 line items, and take 2 photos in airplane mode, then come back online; all 6 ops sync in the order they were created; canonical row returned for any conflict; UI shows `synced` badges.
- A dispatcher edits the same `completed` job from the web dashboard *while* the tech is offline; on sync, one side wins (LWW) and the other is recorded in `conflicts`.
- An upload to MinIO requires zero bytes through the Fastify server.
